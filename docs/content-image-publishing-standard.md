# Content image publishing standard

Applies to all future content and image/template edits. Goal: help readers and make representative images discoverable. Google chooses previews automatically. Neither thumbnail appearance nor click-through improvement is guaranteed. A missing tag alone does not establish the cause of an absent search image.

## Editorial selection and evidence

- Start with the answer and the user's task. Add a visual only when it explains an operation, comparison, geography or evidence better than prose alone. Place it beside the relevant passage, after the direct answer where appropriate. Reuse an accurate existing image when useful; every page does not need a unique cover.
- Prefer actual product screenshots, original explanatory diagrams, or reliable primary-source material. Never fabricate a product interface, weather observation, experiment, game screen, payment/reward receipt, or expert endorsement. AI editorial art must be explicitly identified, never represented as evidence, and is not the default search representative.
- Do not add keyword posters, title cards, unrelated scenery or oversized covers to fill an image quota. A source-derived educational diagram may include labels when needed for understanding; do not turn a title card into a diagram by relabeling it.
- Review the full image, small labels and mobile rendering. Historical weather products must state storm/date and that they are not current. Fictional agency teaching scenarios must remain visibly identified as fictional. Do not alter official labels, invent missing measurements, or imply endorsement.
- Record creator, original source URL, observation/review date, rights/use basis and policy/license URL, modifications and limitations. Agency attribution alone does not establish rights: check third-party credits and restrictions. For a new original composition, retain editable source and the data references. For screenshots, use public or authorized material and remove private information.
- Write accurate concise alt text describing the useful visible information, without keyword repetition. Decorative images alone may have empty alt. Complex diagrams also need a prose/table equivalent. Captions carry source, dates, modifications and limitations; keep source links next to the figure. Do not repeat a long caption verbatim in alt.

## Implementation

- Register reviewed page representatives in `src/data/representativeImages.json`. Each must also appear in the page's normal HTML body as an `img src`, including a fallback img inside picture. The registry does not automatically insert images into prose. Use `ContentFigure.astro` for inline teaching figures. Register an optional `mobileSrc` when the mobile composition differs; retain equivalent facts and labels. The body picture source must match that registered variant and its measured dimensions.
- `SEO.astro` uses the reviewed representative for OG, Twitter, WebPage.primaryImageOfPage and applicable Article/BlogPosting image. The article must describe that page. Use one stable asset URL for reused images. Do not claim an agency image is a HurricaneHub photograph.
- Dimensions come from `src/data/imageMetadata.json`, generated by the build from actual public files. No guessed 1600×900/1200×630 dimensions, low-resolution upscaling or CSS stretching. An unknown remote image needs verified dimensions before use. SVG is supported by Google Images, but sharing platforms often require raster formats; review platform support when selecting new representatives.
- Standard `img`, correct alt, real intrinsic width/height, `height:auto`, responsive maximum width and `decoding=async` are required. Keep small diagrams at or below intrinsic size. Lazy-load below-fold images; prioritize only a genuinely prominent first image. Use an equivalent mobile layout or responsive variants when fine labels become unreadable, and provide a full-size link for maps.
- Compress without removing important labels; inspect the result. The build uses a 750,000-byte review budget for representative assets; this is an internal performance budget, not a Google eligibility rule. Larger evidence images require an explicit documented budget decision and a targeted checker change. Prefer smaller formats/variants while keeping all necessary information.
- Indexable pages retain `max-image-preview:large`. Preserve all noindex/nofollow and preview/staging/404 restrictions, including HTTP headers. The directive permits a size; it does not require Google to display an image. 1200px is not a universal minimum for ordinary search thumbnails. Do not resize an image merely to meet that number.
- Existing generated 1200×630 social cards remain fallbacks while editorial replacements are pending. They are not evidence that useful imagery is complete. Their OG alt must describe the card rather than a different body illustration.
- Template or metadata edits alone do not refresh article publication, source-check or modified dates. Source review dates are not publication dates.

## Release acceptance

1. Review image relevance, authenticity, rights, source links, labels, caption and placement manually. When no suitable material is available, add a specific gap and replacement plan to the audit notes; do not manufacture an image.
2. Run `npm run check` and `npm run build`. Prebuild runs `scripts/verify-content-images.mjs` after OG generation: intrinsic sizes, registered rights/source fields, asset budget, blog body association, alt/captions, placement anchors and mobile file existence. These checks do not certify rights or truth.
3. Against an actual local SSR server run `node scripts/verify-rendered-images.mjs http://127.0.0.1:4321`. This checks registered pages, body/OG/Twitter/schema agreement, served dimensions/MIME/status, robots and noindex preservation. Static dist-only audits cannot cover SSR blogs.
4. Inspect representative historic radar, small CDC diagram, map and responsive teaching diagram on desktop and phone. Record actual `innerWidth/innerHeight`, document client/scroll widths, loaded natural sizes/currentSrc and screenshots. Test at least a narrow phone and a desktop; ensure no horizontal overflow, clipping, distorted aspect ratio or text obscuring the answer. Full-size access does not replace readable neighboring prose.
5. Follow AGENTS version/fetch, selective staging and authorized publishing rules. After deployment verify the actual Worker version/commit, repeat rendered checks on the production origin, and capture production desktop/mobile screenshots. Do not call a local success a production success.
6. Monitor subsequent Search Console image/crawl evidence over time. Absence of a thumbnail in one result does not diagnose a failure; do not promise traffic gains.

## Reproducible original diagrams

The first search-presentation batch uses `node scripts/gen-search-guides.mjs` to retain editable SVG originals and generate native-size PNGs with the existing renderer. Review all regenerated files before staging; it also exports existing radar/season SVGs without upscaling. A generator is an authoring aid, not evidence of factual correctness. Dated interface screenshots are captured separately from the actual public interface, with the displayed observation time and limitations recorded.
